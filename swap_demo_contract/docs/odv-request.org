* Overview
This document outlines the integration process for the On-Demand Validation (ODV) request transaction system in the Charli3 Oracle network. ODV requests allow smart contracts to access real-time, multi-source exchange rate data when needed.

* Command Interface

You can access the ODV request functionality through the CLI:

#+begin_src bash
λ > charli3 ogmios preprod send-odv-request --help
usage: python main.py [{ogmios}] [{preprod}] send-odv-request [-h]
Generate a request for information by prepaying the Charli3 oracles.
options:
  -h, --help  show this help message and exit
#+end_src

To execute an ODV request, connecting with all nodes, requesting data, signing the transaction, and submitting it to the blockchain:

#+begin_src bash
poetry run odv-demo ogmios preprod send-odv-request
#+end_src

The command automatically calculates the required C3 tokens for the aggregation service.

* Payment Calculation

** Static Payment Example

Let's examine how payment is calculated using a sample ODV oracle contract configuration:

#+begin_src yml
oracle_settings:
  os_node_list:
    [
       "49bd983d12353a48d39ad15212220ebd71dd3f897eb29ab89f3cb58e",
       "8e9ed3986a773db2420b0604357a65f5d9d26d094279918ad405fdca"
    ]
  os_updated_nodes: 10000 # 100%
  os_node_fee_price:
    node_fee: 1500000 # 1.5 C3
    aggregate_fee: 2500000 # 2.5 C3
    platform_fee: 1000000 # 1 C3
#+end_src

The payment calculation works as follows:

1. Identify required nodes from `os_node_list` (2 nodes in this example)
2. Check the percentage of nodes required via `os_updated_nodes` (100% in this example)
3. Calculate the total payment:
   - Node fee × Number of required nodes: 1.5 C3 × 2 = 3 C3
   - Add aggregate fee: 2.5 C3
   - Add platform fee: 1 C3
   - Total: 6.5 C3 (6,500,000 lovelace-equivalent token units)

** Dynamic Payment

For dynamic payment scenarios, an external Charli3 oracle contract handles price conversion. For example:

#+begin_src yml
oracle_settings:
  os_node_list:
    [
       "49bd983d12353a48d39ad15212220ebd71dd3f897eb29ab89f3cb58e",
       "8e9ed3986a773db2420b0604357a65f5d9d26d094279918ad405fdca"
    ]
  os_updated_nodes: 10000 # 100%
  os_node_fee_price:
    node_fee: 1500000 # 1.5 ADA
    aggregate_fee: 2500000 # 2.5 ADA
    platform_fee: 1000000 # 1 ADA
  rate_nft: Union[SomeAsset, NoDatum]
#+end_src

The key difference here is that values are denominated in ADA but paid in C3 tokens at the current exchange rate.

The payment token is configured in the `config.sample.yaml` file:

#+begin_src bash
  payment_token: # Reward token
    policy_id: c9c4ada29e8640077a03ec2a6982f867f356ba1d7e25d19232372828
    asset_name: TestC3 # Test Charli3 (TestC3)
#+end_src

The exchange rate for dynamic payment is set in the oracle configuration datum under C3 Coresettings.

The asset structure is defined as:

#+begin_src bash
@dataclass
class SomeAsset(PlutusData):
    """Represents a native token asset"""
    CONSTR_ID = 0
    asset: Asset

@dataclass
class Asset(PlutusData):
    """Represents a native token asset"""
    CONSTR_ID = 0
    policy_id: PolicyId
    name: AssetName

    def __post_init__(self) -> None:
        # Add validation for policy_id length (28 bytes for Cardano)
        if len(self.policy_id) != 28:
            raise ValueError("Policy ID must be 28 bytes long")
#+end_src

Example: If the ADA/C3 exchange rate is 4.9 ADA per C3, and the total fee in ADA is 6.5 ADA, then the payment would be 6.5 ÷ 4.9 = 1.33 C3, or 1,330,000 token units.

Users can send any amount of C3 tokens, but the contract will only create an aggregation if the minimum required amount is covered. Any excess goes to the platform administrator, while nodes receive their predefined rewards.

* Off-Chain Integration Process

The `send-odv-request` implementation follows a comprehensive workflow (main.py):

1. **Initialization and Configuration**
   - Load configurations and establish network connection
   - Initialize the ODV client (`ODVClient`)
   - Calculate validity window for the request

2. **Node Feed Collection**
   - Request feed updates from all configured nodes
   - Process and verify node responses
   - Collect statistics on successful responses

3. **Transaction Construction**
   - Build an aggregate message from node responses
   - Construct the ODV transaction with payment information
   - Prepare transaction parameters including validity window and reward tokens

4. **Signature Collection**
   - Send the constructed transaction to oracle nodes for verification
   - Collect cryptographic signatures from participating nodes
   - Verify sufficient signature threshold is met

5. **Transaction Finalization**
   - Attach collected signatures to the transaction
   - Submit the fully signed transaction to the blockchain
   - Monitor transaction status to confirm successful processing

6. **Error Handling**
   - Handle transaction processing errors
   - Manage network-related exceptions
   - Provide detailed status reports throughout the process

The implementation utilizes asynchronous programming to efficiently handle concurrent requests to multiple oracle nodes, ensuring optimal performance during the data collection and signature gathering phases.

When successful, the transaction will be confirmed on the blockchain, making the oracle feed data available for consumption by smart contracts in the same block as the ODV request.

** Integration Considerations

When implementing your own ODV client:

1. *Network Resilience*: Design for partial success scenarios where some nodes may be unavailable
2. *Timeout Management*: Set appropriate timeouts for node communication
3. *Signature Verification*: Always validate node signatures before processing data
4. *Transaction Building*: Ensure proper handling of the two-phase process (data collection → transaction signing)
